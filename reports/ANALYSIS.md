# 新北 YouBike 六個月資料分析與調度優化建議

資料：2026-01-01 至 06-30，12 份 CSV，13,324,945 筆，1,583 個站點鍵。每一檔都已逐檔解碼、驗證 SHA-256 並剖析。

**貫穿全文的界線**：快照庫存差不是真實借還需求。同一個 30 分鐘區間內一借一還會互相抵銷；站點零車時，想借而未借到的人不會出現在資料裡。因此所有流量數字都是**下界**，真實需求只會更高。

## 三、服務損失在哪裡

- 零車的半小時觀測共 **754,396** 次，其中 **263,269** 次（約 35%）落在需求最高的十六個時段。
- 需求最高時段集中在 06:30 至 09:00 與 16:00 至 20:30，與通勤尖峰吻合。
- 雙零比例達 30% 以上的站有 **41** 個，鎖住 **1,117** 個車柱，占全市 2.4%。集中在牡丹車站、野柳地質公園、猴硐火車站、白沙灣、雙溪車站等觀光與偏遠站點。**必須先查核營運狀態，不是派車就能解決。**
- 另有 **5** 個站共 109 個車柱，全期庫存幾乎不變且每日流量低於 1，包含汐止區綜合運動場、同興大同路口、景平橋和路口。這些不是缺車，是**沒有被使用**。

## 四、關鍵發現：多數缺車不需要派車

在全部 754,396 次零車觀測中：

| 處置方式 | 觀測數 | 占比 |
|---|---:|---:|
| 300 公尺內有鄰站可借（步行約 5 分鐘） | 464,338 | 61.6% |
| 500 公尺內有鄰站可借 | 590,898 | 78.3% |
| 500 公尺內沒有替代資源，只能派車 | 163,498 | 21.7% |

另有 **88** 個站在 500 公尺內完全沒有鄰站，缺車時只能靠派車，應列為最低服務保障對象。

**這是整個調度策略的支點**：近八成的缺車情境，只要在使用者出發前告訴他「走五分鐘到隔壁站」，就不必出動一趟車。派車資源應集中在剩下的兩成，以及偏遠無替代的站。

提醒：鄰站當下有車只代表候選資源存在，不等於使用者走得到、走到時還有車，也不等於改善率。這個數字要靠實地試辦驗證。

## 七、調度優化策略：四層處置

依上面的數字，把每一個「可能缺車」的情境依成本由低到高排序，只在必要時才出車。

**第一層：出發前資訊分流（成本最低，覆蓋最廣）**
近八成的缺車情境在 500 公尺內有替代站。民眾端在出發前就推薦「借哪一站、還哪一站」，並顯示到站時的預估車數與零車機率，把人流導到還有車的站。這一層不需要任何車輛移動。需要驗證的是使用者實際接受率，目前以 0.7 的轉換率假設呈現。

**第二層：獎勵導引（成本次低）**
對「從預測將滿的站借、還到預測將缺的站」的旅次給點數與城市章。獎勵額度依目的站當下與預測容量動態調整，避免把另一站塞滿。這一層把使用者本來就要走的路變成調度力，邊際成本只有獎勵成本。

**第三層：提前 120 至 180 分鐘預置（真正的派車）**
早尖峰缺口 1,195 輛、晚尖峰 1,862 輛，全市同時段的可抽出量分別是 4,348 與 3,146 輛，總量足夠。以載量 20 輛計，早尖峰 60 趟、晚尖峰 94 趟。因為從決定到人車抵達至少一小時，這些趟次必須在尖峰前兩到三小時就排定，這正是 120／180 分鐘預測尺度存在的理由。

**第四層：狀態查核（不是調度問題）**
41 個雙零站鎖住 1,117 個車柱、5 個站完全沒有使用。這些送車過去也不會被借走。應先確認營運狀態、場地與需求，再決定是復役、移設還是縮柱。把它們從派車清單排除，可以讓調度人力專注在真正有需求的兩成情境。

## 八、要讓使用率最大化，優先做這五件事

1. **先把資訊分流做起來**。近八成缺車有替代站，這是投報率最高的一步，而且不需要營運商開放任何控制權。
2. **派車只做兩成**。集中在 500 公尺內沒有替代資源的情境，以及 88 個無鄰站的孤立站。
3. **尖峰前兩小時排程，不要等失衡發生**。一小時的前置時間是硬限制，60 分鐘內的突發只能靠已在勤資源與民眾分流。
4. **清查 41 個雙零站與 5 個零使用站**。1,226 個車柱目前沒有產生任何服務，這是最容易被誤判成「缺車」的部分。
5. **車柱重新配置**。把周轉極低的大站車柱移到常態無位可還的高周轉站，這比增購車輛便宜。

## 九、用 AWS 怎麼做

| 層次 | 服務 | 做法 | 現況 |
|---|---|---|---|
| 資料湖 | Amazon S3 + AWS Glue + Amazon Athena | 原始快照轉 Parquet 後放 S3，Glue 建目錄，Athena 直接下 SQL，不必先搬進資料庫 | 已完成，1,332 萬筆可查 |
| 即時擷取 | Amazon Kinesis Data Firehose | 新北開放平台每五分鐘的即時資料直接寫入 S3，自動分區，補上歷史檔缺少的營運狀態與車種欄位 | 建議新增 |
| 特徵與訓練 | Amazon SageMaker AI | 訓練作業產出四個尺度的預測模型，與本機共用同一份特徵程式 | 已完成一次成功作業 |
| 模型管理 | SageMaker Model Registry | 每次訓練註冊版本與指標，上線前比對，避免用舊模型 | 建議新增 |
| 定期重訓 | Amazon EventBridge Scheduler + SageMaker | 每週自動重訓與回測，指標退步就不上線 | 建議新增 |
| 推論 | SageMaker 端點或 AWS Lambda | 全市 1,583 站 × 四個尺度的批次推論，每半小時跑一次 | 建議新增 |
| 生成式 AI | Amazon Bedrock | 推薦理由、調度簡報、工單摘要。數字一律由模型與規則算好再交給它改寫 | 已完成 |
| 路網 | Amazon Location Service Routes | 步行、騎乘、調度車三種模式的真實路線與繁體中文指示 | 已完成 |
| 地圖 | Amazon Location Service Maps | 底圖與衛星圖磚，由伺服器代簽 | 已完成 |
| 應用狀態 | Amazon DynamoDB | 意向、工單、告警、任務 | 已完成 |
| 告警派送 | Amazon SNS 或 Amazon Pinpoint | 正式上線後把站點告警送到調度人員手機 | 需真實使用者與同意流程，本案不做 |
| 儀表板 | Amazon QuickSight | 給不進系統的主管看的週報與月報 | 建議新增 |
| 監控 | Amazon CloudWatch | 資料延遲、模型漂移、API 失敗率的告警 | 建議新增 |
