# 驗收指標定義（政府端「驗收指標」面板）

實作：`app/metrics.py`、`/api/metrics/*`、`app/static/gov.html` 的 `驗收指標` 面板。
目的：讓「服務中斷偵測與調度改善」這件事可被第三方用同一份資料重算，而不是只看畫面上的示範。

資料來源是 2026-01-01 至 06-30 的站點庫存快照，每站每 30 分鐘一筆。**它不是借還交易紀錄。**
因此以下所有數字都是站點可用性的觀測，沒有任何一個是需求、失敗旅次或到站成功率。

## 一、服務中斷事件

### 事件怎麼切

對每一站的時間序列，取連續的「可借＝0」（缺車）或「可還＝0」（缺位）快照為一段事件。

排除下列站‧分箱，它們是**待查狀態，不是服務中斷事件**：

| 排除 | 條件 | 理由 |
|---|---|---|
| 雙零 | 可借＝0 且 可還＝0 | 分不出是站點停用、資料未更新還是真的同時無車無位 |
| 長期不變 | `flat_run ≥ 48`（24 小時庫存無變化） | 多為停站或資料未更新，不是當下的服務中斷 |
| 容量矛盾 | 可借＋可還 > 總車柱（入庫時已隔離，共 10,468 筆） | 容量版本無法判定，不修成看似合理的值 |
| 無資料 | 該分箱沒有觀測 | 缺測不視為恢復，也不視為持續中斷 |

缺測會**切斷**事件並標記，不會把兩段接起來假裝是一段。

### 持續時間只有範圍，沒有單一值

30 分鐘一筆的快照無法給出精確起訖，只能給上下界：

- **觀測下界** ＝（最後一筆零快照 − 第一筆零快照）× 30 分鐘。
  只出現一筆零快照時下界為 **0 分鐘**——資料無法證明它持續了多久。
- **可能上界** ＝（事件後第一筆正常觀測 − 事件前最後一筆正常觀測）× 30 分鐘。
  前後相鄰都有正常觀測時，上界剛好是下界 ＋ 60 分鐘。
- 事件延伸到期間邊界，或相鄰是缺測時，**上界不收斂**，面板標示「上界未收斂」。

面板上「超過 30／60／120 分鐘」同時給兩個數：下界口徑是**確定達到**的件數，上界口徑是**最多可能**的件數。兩個數字都要看。

### 彙總指標

| 指標 | 定義 |
|---|---|
| 事件數 | 上述切法的事件總數，含只有一筆快照的事件 |
| 超標站分鐘（下界） | `Σ max(0, 下界 − 30)`，30 分鐘為訪談轉述的恢復目標 |
| 超標站分鐘（上界） | 同式改用上界；上界未收斂時以「下界＋30 分鐘」保守代入 |
| 恢復時間 P50／P90 | 下界與上界各自取分位數 |
| 受影響站數 | 期間內至少發生過一次事件的站 |
| 資料中斷段 | 缺測的連續段數與站‧分箱數 |

**恢復目標 30 分鐘來自主管訪談轉述，不是官方 SLA，也還沒確認是否全站適用。**

## 二、告警門檻取捨

用 `reports/model_eval.json` 六月測試期的校準分箱，換算「門檻 → 告警量／精準度／召回／誤報」。

限制：

- 門檻只能落在校準分箱邊界（每 0.1），不是連續掃描。
- 告警量是全市 1,583 站、六月 720 小時的每小時平均。
- **≥0.9 那一箱幾乎都是「當下已經零車且延續」**，會把整體精準度墊高到 99%。整體精準度不代表預警能力，
  新發生事件的召回（120 分鐘尺度、缺車、@0.5 為 **10.9%**）才是。

面板直接呈現的結論：

> 門檻拉到 0.9，全市每小時仍會發出約 62 則（缺車／120 分）；真正新發生的事件本來就有每小時約 84 件。
> **把門檻調高不會把告警量降到值班可處理的範圍。** 要降量必須改變告警定義——只對新發生、
> 且 500 公尺內沒有替代站、需要派車的情況發告警，並以行政區或站群彙總，而不是逐站逐則。

（「500 公尺內沒有替代站」的比例見 `reports/ANALYSIS.md`：全期零車觀測中 21.7% 在 500 公尺內沒有其他可借站。）

## 三、流程時效（本場回放，非實測）

- 時間戳來自**回放時鐘**。
- 告警開啟與條件自動解除由觀測與預測觸發；確認、轉調度是人在介面按下的真實動作；
  出車、抵達、完成是依 `planner.ASSUMPTIONS` 推進的**模擬狀態**。
- 「條件自動解除」＝站點恢復有車，**不代表有人去處理過**。
- 未指派比例 ＝ 1 −（已確認 ÷ 開啟的服務事件）。
- 調度方案的里程、搬運車輛、準時比例來自 `planner.py` 的可行性計算，尚未接真實派工系統。

樣本數在一場 demo 內很少，只能看趨勢，不能當統計結論。

## 四、這一版量不出來的

| 指標 | 需要的資料 | 為什麼現在不能算 |
|---|---|---|
| 診斷分流正確率（車輛／車柱／站端） | 車號—柱號對應、租借錯誤碼、設備心跳、維修驗收結果 | 只有站點層級庫存，沒有單車或車柱識別，建不了真值 |
| 通知送達率與手機確認時間 | Web Push 訂閱、平台回執、開啟與確認事件 | 目前是頁內即時通知，沒有背景推播，送達與否無法量測 |
| 調度改善的實際成效 | 試辦對照組與同期真實借還紀錄 | 回放只能算模擬方案的預計補足，沒有對照就不能說成實測 |
| 失敗旅次與到站成功率 | 借還交易與 App 查詢紀錄 | 快照零車不等於有人借不到；鄰站有車不等於走得到 |

列在面板上是為了不把做不到的事說成做得到。取得對應資料後，同一套面板就能補上。

## API

| 端點 | 參數 | 回傳 |
|---|---|---|
| `GET /api/metrics/service` | `window=day\|week\|month\|all`、`kind=empty\|full` | 事件彙總、時段與行政區分佈、最嚴重站點、最長事件、排除統計 |
| `GET /api/metrics/threshold` | `horizon=60\|120\|180`、`kind`、`duty`（每小時可處理則數） | 門檻取捨表、新發事件指標、結論 |
| `GET /api/metrics/flow` | — | 各段耗時、事件處理漏斗、調度方案彙總、無法量測清單 |

`window` 以回放時鐘當下為終點往回推；`all` 為 1–6 月全期（全站全期約 1.1 秒算完，結果依 (期間, 類型) 快取）。
