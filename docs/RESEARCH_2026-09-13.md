2026-09-13。本檔是調查記錄，不是結論或已核准的實作方向。
所有外部數字都標出處；所有「實測」都是本次親自跑出來的，指令附在各段。

# 一、開源作品調查

## 1.1 taipei-doit/YouBike-Optimization（臺北市資訊局，15 stars，Apache 2.0）

<https://github.com/taipei-doit/YouBike-Optimization>

**只開源了選址需求模型（`Potential-Demand/`），調度優化那半沒有開源。**

方法：臺北市切 4,309 個 250m×250m 網格；悠遊卡交易當 target（每小時借出／歸還次數）；
有站的網格當訓練資料，無站的網格當推論資料；LightGBM + XGBoost + CatBoost **ensemble**，
Optuna（TPESampler）調參；最後用一個公式把預測的借還次數換算成建議柱數與初始配車數。

特徵面（`preprocess.py`）比我們廣很多：信令人口（年齡層／工作人口／居住人口／遊客）、
捷運出入口數與進出站人次、公車站與路線數、人行道面積、標線型人行道面積、自行車道長度、
行道樹數、路燈數、路網面積與比例、快速道路／省道／市區道路長度、坡度與坡度分級、
地表高程、NDVI、綠覆率、開發強度（商業／混合／住宅比例）、土地利用 11 類比例、
POI 13 類的店家數與評論數與評分總和。

### 值得學的三件事

1. **`src/detect/abnormal.py`：把「空站」變成事件的程式化定義。**
   兩個參數 `tolerate_num`（容忍幾台車以下算空）與 `tolerate_time`（連續超過幾分鐘才算數），
   並且處理了跨小時區間的切分（同小時內、跨一個小時、跨多個小時三種情況分開累計）。
   **這正是主管訪談裡「空站約 30 分鐘可接受」的程式化版本。** 我們的事件台帳有分級，
   但沒有把「容忍台數」做成參數——目前是硬性的「零車」。

2. **同一份特徵、兩個 target（`on`/`off` 借與還分開建模）。**
   他們沒有把借還混成一個「需求」，而是各訓一組模型。我們的做法一致（reg_bikes／reg_spaces、
   cls_empty／cls_full），這點可以互相佐證。

3. **選址結論要能被否決。** README 明說「不是所有無站網格都需要設站，山區等不適合的
   不會出現在建議清單」——先用規則篩掉，再讓模型排序。我們的待查清單是同樣的精神。

### 他們程式裡的一個關鍵細節（對我們的論述很重要）

`abnormal.py` 算滿站時用的是：

```python
df['available_return_bikes'] = df['capacity'] - df['available_rent_bikes']
```

**空位是用「容量減車數」推算的，不是讀真實的可還柱數。** 也就是說，
壞掉的柱位在這個算式裡會被當成「可以還車」。這是名目庫存的算法，
不是服務可用性——見第三節的實測。

## 1.2 tses89214/youbike-historical-data（7 stars）

<https://github.com/tses89214/youbike-historical-data>

動機和我們一模一樣：「公開數據只有即時，沒辦法知道『我家旁邊的站點何時會補車』
『沒車的時段大約是幾點』」。做法是每 10 分鐘打一次台北的即時 API，切成
`sites`（維度表）與 `slots`（事實表），每天凌晨上傳前一天資料到 GitHub。

**這個 repo 的 Note 段落，等於是外部獨立發現了我們資料裡的三個坑：**

- 「有些情況下 `total != available_rent_bikes + available_return_bikes`，
  可能站點上面有停止服務的車輛等等。」→ 我們的**容量矛盾**待查項，被別人獨立踩到。
- 「不是所有站點都會上傳數據，有些站點最新的更新數據是過去好幾個月的。」
  → 我們的**資料新鮮度／24 小時無變化**待查項。
- API 有多個時間欄位（站點上傳時間 vs YouBike DB 接收時間），他選 `infoTime`（站點上傳時間）
  「比較有參考價值」。→ 我們的**最後資料時間**欄位該用哪一個，有了外部依據。

**可引用價值高**：我們講「快照資料有這些坑」時，不是自說自話。

## 1.3 nathanmarinas2/bicicoruna-fleet-optimization（西班牙 A Coruña，MIT）

<https://github.com/nathanmarinas2/bicicoruna-fleet-optimization>

**本次調查中與我們最像的對照組**，而且做到上了西班牙《El Español》地方版
（2026-02-23，標題〈一位 UDC 學生的專案：「它有 16% 的時間是壞的」〉），
市議會公開肯定。79 站、670 台車。

做法：自建 GBFS scraper（`collector.js`，Node.js 部署在 Railway，每 5 分鐘，
容錯並處理資料缺口）→ 建立公開不存在的歷史時序 → 特徵工程（週期編碼、時間落差、天氣、趨勢）
→ LightGBM 二元分類器預測 30 分鐘內的缺車 → K-Means 把站分成 4 種功能原型
（住宅／工作／休閒／混合，用手肘法驗證）→ 營運風險與 ROI 分析 → Streamlit + Leaflet 儀表板。

### 值得學的五件事

1. **重新定義「空站」門檻：從 0 台改成 <5 台。** 理由寫得很直白——
   「提高營運敏感度、避免缺貨」。等到 0 台才算空站，對營運來說已經太晚。
   這和台北 `tolerate_num` 是同一個思路，**我們目前用的是硬性零車，這是可以改進的點。**
2. **把不平等量化成一句能上新聞的話。** 「邊陲住宅區 16% 的時間完全沒車，
   市中心與海岸站則有車」——一個數字、一個對比、一句話。
3. **「零成本」框架。** 他們的結論是：只要把 27 台車從低週轉站調到關鍵站就能解決崩潰，
   **不需要新的公共投資**。這比「請多買車」有說服力得多，也正好對應台北的閒置車移撥。
4. **Transfer Learning：巴塞隆納 → 科魯尼亞**，用大城市預訓練、小城市微調。
   對我們的啟發是「台北的資料能不能遷移到新北」，但我們沒有台北的交易資料，列為未來工作。
5. **有 ROI / Business Impact 專章。** 我們目前沒有。

### 不能拿來比較的地方

他們的 F1 0.78／Accuracy 87% 是「30 分鐘內 <5 台」的二元分類，
與我們「新事件（現在正常、未來為零）」的定義**完全不同**，兩組數字不可互相比較，
也不可宣稱我們比較好。我們的前置時間 30／60／120／180 分鐘比他們的 17–30 分鐘長，
是因為對齊「人車至少 60 分鐘才到」的營運現實，這是取捨不是優劣。

## 1.4 aaron1aaron2/GMAN-based-Forecasting-of-YouBike-Shortages-in-Taiwan（政大課程專案）

用 GMAN（Graph Multi-Attention Network，交通流量預測的知名模型）預測台北站點存量，
含自建爬蟲（每 10 分鐘）。**技術路線參考：把站點網路當成圖，用圖注意力捕捉站間關聯。**
我們目前用的是站點矩陣特徵（鄰站 500m），沒有做圖模型。
交件前不動模型，列為未來工作。

## 1.5 stephensavoia/rebalancing_minimizer（Bike Share Toronto）

**觀點最新穎的一個。** 目標不是預測需求，而是預測「**新設一個站會給調度團隊帶來多少負擔**」，
target 是 ride-end ratio（在該站結束的趟次 ÷ 該站起訖總趟次），
predictor 只用經緯度與高程。README 自己說明這不該是唯一決策依據。

**對照台北的選址模型：台北只預測需求（借還次數），沒有預測調度成本。**
一個高需求但借還極度不平衡的站，會變成永久的調度黑洞。
這是「選址」與「調度」之間沒有接上的縫，值得記下來。

# 二、資料可得性：悠遊卡與借還交易

**結論：悠遊卡交易資料（借還起訖 OD）不是開放資料，我們拿不到，也不該假裝拿得到。**

| 資料 | 可得性 | 證據 |
|---|---|---|
| 悠遊卡去識別化交易資料 | **不可公開取得**。台北是由悠遊卡公司**專案提供**給大數據中心 | repo README 致謝段明列「de-identified data provided by **EasyCard Corporation**」，屬合作關係而非開放平台 |
| 信令人口（遠傳） | **不可公開取得**，同上為專案提供 | 同上，致謝 Far EasTone |
| 新北 YouBike2.0 即時站況 | **可取得，已實測打通** | `data.ntpc.gov.tw` 資料集 `010e5b15-...`，每 5 分鐘，免費，政府資料開放授權 1.0 |
| 台北 YouBike2.0 即時站況 | **可取得，已實測打通** | `tcgbusfs.blob.core.windows.net/dotapp/youbike/v2/youbike_immediate.json`，每 1 分鐘 |
| 台北「即時資訊 OD」資料集 | 名稱裡的 OD 是 Open Data 不是 Origin-Destination，**內容仍是即時站況**，不是歷史起訖 | 已查 data.taipei 資料集頁，18 個欄位全是站況欄位 |
| 歷史借還紀錄 | 有第三方說台北有按月 ZIP，**本次未查證到可用連結，且被指出各月欄位定義不一致**。列為待查，不要寫進簡報 | — |

# 三、本次實測發現（全部是這次親自跑出來的）

## 3.1 官方即時 API 的「總格數 ≠ 可借 ＋ 可還」是全系統性現象

2026-09-13 00:34 抓全量即時資料：

| | 站數 | 容量矛盾站數 | 比例 |
|---|---:|---:|---:|
| 新北 | 1,606 | **553** | **34.4%** |
| 台北 | 1,800 | **921** | **51.2%** |

大多數是差 +1（可能是保留柱位或一台待處理的車），但也有整站型的：

- 三芝淺水灣：總 48、可借 0、可還 0，**差 +48**，而 `act=1`（顯示啟用中）
- 大安溫州停車場：總 5、可借 0、可還 0，**差 +5**

**這個差額就是「名目上存在、但既借不到也還不了」的柱位與車輛。**
見車率（≥1 台車的時間比例）與見位率（≥1 個空位的時間比例）**都不會反映它**，
因為兩者都只看單邊的數量，不看兩者加起來對不對得上容量。

> 這推翻了我原本把「雙零」當成資料異常排除的處理。
> 淺水灣此刻 `act=1`、總 48 格、借還皆 0——這比較像**整站服務中斷**，不是資料錯誤。
> 我們的待查清單把雙零列進去是對的，但語意應該是「整站不可用（待查）」而不是「資料異常」。
> **這一條會影響 `reports/gap_vs_taipei.py` 的排除邏輯，尚未修改，先記錄。**

# 四、我們手上資料的問題清單

1. **半小時快照，不是連續時間。** 所有比例都是快照比例，不能講成連續中斷時長，
   也不能講成失敗旅次。兩筆零值快照之間可能已經恢復又空掉。
2. **雙零快照 187,472 格、涉及 69 站。** 語意未定：可能是整站服務中斷（見 3.1），
   也可能是資料中斷。目前被當異常排除，**這個處理需要重新檢討**。
3. **停用／退場站 25 站**（六月整月零車）。不剔除就會霸佔「缺車最嚴重」排名前幾名
   ——國慶三樹路口 1 月見車率 99.3%、3 月起 0%；興華公園 4 月 29%、5 月起 0%。
   **這是退場，不是調度失敗。**
4. **容量矛盾未判定根因**（見 3.1），且我們的歷史資料裡沒有可還柱數的獨立欄位可交叉驗證。
5. **沒有借還交易（OD）**，所以無法算真實需求、無法算失敗旅次、無法做站點替代性的行為驗證
   ——我們的鄰站是**直線距離**推的，台北的替代性是**借還行為**推的，兩者不等價。
6. **沒有車號／柱號／錯誤碼**，所以無法可靠區分壞車、壞柱、車機、站端網路。
7. **沒有車隊位置、班表、載量、工時、倉儲庫存**，所以派車、ETA、改派方案都是情境假設。
8. **沒有巡查紀錄**，所以「任務清單沒有這一站」只代表排程沒涵蓋，不能推論沒有人到過現場。
9. **零車新事件召回偏低**（180 分 0.131），不可只用 MAE 進步宣稱預警完整。
10. **模型凍結中**，交件前不重訓、不重跑管線。

# 五、三端痛點盤點

來源：使用者轉述的主管訪談、`docs/DIRECTION_REVIEW_2026-09-12.md`、三份 HANDOFF。
**訪談內容是輸入，不是已核實的正式 SLA 或全台制度。**

## 5.1 政府端（新北市交通局）

| # | 痛點 | 現況為什麼痛 | 我們已有／缺什麼 |
|---|---|---|---|
| G1 | 空站沒有「案件」 | 儀表板紅點是狀態，不是案件。沒有持續多久、誰負責、幾點恢復 | 已有事件台帳（P0／P1／長期／待查）、負責人、狀態留痕 |
| G2 | 指標看不見尖峰 | 見車率／見位率是 18 小時平均，早峰 2 小時的失效被稀釋成綠燈（見 3.4） | 已可算，**尚未放進政府端畫面** |
| G3 | 名目庫存不等於服務可用 | 官方可借數不扣壞車；容量矛盾 34.4%（見 3.1） | 已有服務可用性三欄並列不相減 |
| G4 | 資料缺失被誤當恢復 | 站點停止上傳，畫面上看起來就「不是零車了」 | 已有最後資料時間與資料中斷事件，**與空站事件分開** |

# 六、這次調查改變了什麼

1. **「台北沒處理還不了」是錯的** —— 見位率存在、即時地圖的紅色就是無可還車位、
   且即時圖涵蓋新北。差異化不能建立在這句話上。
2. **真正的縫是時間尺度與指標涵蓋範圍**：月平均看不到尖峰（3.4）、
   即時紅點看不到 30–180 分鐘後、名目庫存看不到 34.4% 的容量矛盾（3.1）。
3. **「空站門檻」應該是參數不是常數** —— 台北與 BiciCoruña 都這樣做，我們沒有。
4. **雙零的語意要重新判定** —— 可能是整站服務中斷，不是資料異常。
5. **`docs/POSITIONING.md` 的第二節有兩條是錯的，必須改寫**；
   `reports/gap_vs_taipei.py` 的排除邏輯要重新檢討。兩者都尚未修改。
