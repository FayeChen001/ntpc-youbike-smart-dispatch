# 訪談後的產品方向與程式盤點（討論稿）

基準：main / 5faad73。2026-09-12 讀取原始碼與現有文件；本輪未重新訓練模型、驗證雲端部署或修改功能。使用者轉述主管訪談：空站約 30 分鐘可接受、部分站空 1–2 小時；人員靠經驗調度；熱點車輛 72 小時未租可能被列為疑似故障。以上是訪談輸入，不當成已核實的全台制度或正式 SLA。

## 建議主軸

讓每一個長時間無法借還的站點，都有可追蹤的原因、負責人與恢復時間。

政府端掌握事件與資源決策；營運端執行有證據的派工；民眾端提供借還意向、分流與異常證據。保留三端，開發重心先轉向「發現→確認→指派→抵達→恢復→原因復盤」。

## 程式現況與需優先處理事項

- 已有 FastAPI / SSE / 三端介面、歷史回放、30/60/120/180 分鐘模型、Bedrock 摘要、活動與氣象服務、調度組趟及報修。
- server.py evaluate_alerts：三筆半小時零值快照，訊息寫成連續 90 分鐘；首尾其實相距 60 分鐘，且快照不能證明期間沒有恢復。改採時間戳、缺測標記與「觀測到的空站區間」；即時資料也只宣稱觀測連續性。
- 告警每步超過 8 則直接 continue，沒有寫入事件清單，與摘要文案宣稱「已併入清單」不一致。所有事件先持久化，再對通知節流；P0 升級不可被一般摘要吞掉。
- 現有服務主要為回放狀態；取得即時 API 不等於預測、告警全流程已使用真實時鐘與即時資料。
- sw.js 只有快取，沒有 push / notificationclick；頁內 SSE 不是手機背景推播。
- planner.py 最近鄰貪婪、假設車容量／速度／行政區中心為出發點，並非真實車隊最佳化。缺真實排班、GPS、載量、工時與倉庫库存。
- 部分缺口送不到全量後，程式仍把該站從 deficits 移除；需保留殘量。120/180 分鐘方案需共用資源帳，避免重複承諾庫存與人車。這些為靜態閱讀發現，需針對性測試。
- 目前每站固定目標時間的可行性只用第一個送站抵達判定；須檢查每個送站的服務時限。
- 60 分鐘「決策到抵達」訪談與程式「60 分前置再加路程」語意不同。拆出人員準備、取車、行車、卸車時間後再校準。
- tickets 以站點＋問題類別＋2 小時去重，未以車號／柱號去重，可能合併不同設備；缺 asset_type、dock_id、error_code。
- 模型卡的 120 分鐘新零車事件召回 @0.5 為 10.9%，不可只以 MAE 進步主張預警完整。重新以值班可處理告警量、召回、誤報與提前量選門檻，後續用新時段驗證。
- STATE 為全域示範狀態，正式多使用者、權限、狀態恢復與任務原子性仍須另建。主管手機決策不能只連到無身分驗證的展示動作。

## 1. 空站事件與主管手機決策

事件分三條：無車／無位服務事件、設備可用性事件、資料中斷事件。資料缺失不可視為恢復，也不可自動視為空站。

建議試行分級（待主管確認，不是官方標準）：

- P2：120–180 分鐘將失衡，進入值班排程，不逐則打擾主管。
- P1：觀測空站達 20 分鐘且預估無法在 30 分鐘前恢復，或已超過 30 分鐘；通知值班調度。長時間空站即使冷門仍需有案件。
- P0：超過 60 分鐘仍無可執行的恢復計畫、關鍵站群同時失效，或 P1 超過約定期限無人接手；通知主管與值班主管。實際門檻與接手期限待議。

30 分鐘是恢復目標，不是開始準備的時間：人车通常至少 60 分鐘才到，應用 120/180 分鐘預測預排；現場事件由已在勤資源、鄰站引導與分流補位。高風險站不能等空了才預警。

主管卡片：站名、觀測空站多久、最後資料時間、服務影響代理指標、已確認原因／待查假說、目前負責人、現行 ETA、方案 A/B 的資源與受影響站點、超時原因。例：就近車隊改道 18 分抵達但原任務延後 7 分；跨區支援 32 分且增加 4 km（皆需標示模擬或實際來源）。

通知點入行動頁，重新確認最新任務版本，再選「同意改派／要求跨區支援／指定負責人」。保存決策、理由、版本與時間，防止雙重派工。推播發送、平台接受、使用者開啟、明確確認分開記錄；不宣稱保證送達。未確認升級到備援通知管道。

原因時間線：需求暴增、沒排到任務、無可用人車、無供給、已派但塞車、接單延遲、設備故障、資料過期。每個原因須連結任務/GPS/供給/設備/資料證據，缺證據顯示待查。只有庫存快照，無法證明「人員沒有去」。

## 2. 動態調度與排班

優化目標先減少超過服務目標的空滿站分鐘，再減少里程、工時和重排干擾；增加最久未服務站保障，避免一直救熱門站。

採兩層：前一天依日型、活動、學區與通勤預測安排班次和待命區；當天每 5–10 分鐘或重大事件重新評估未執行任務。已執行與下一個確認站先鎖定，效益不足時不更改。

輸入：車隊位置、容量、健康車/故障車載量、人員上下班/休息/資格、各站未來供需、道路時間、裝卸時間、供給保留量、維修站能力。輸出：哪台車、何時、哪站取幾台、送幾台、各站 ETA、剩餘缺口、選擇依據及不可服務原因。

以帶取送、容量、時間窗的路線規劃為方向，維持現有貪婪方案當基準；只宣稱求解器在時限內找到的可行改善方案，不宣稱全域最優。無真實車隊先用清楚標示的資源情境。

創意：同趟運健康車補站並回收故障車，但故障車佔載量且不算供給；先驗證交換取送、容量守恆和維修目的地資格。主管亦可比較「加一台車／調整一個班次」能改善哪些未服務缺口。

## 3. 借不到，不等於車壞掉

民眾按「借不到／還不了」，不先強迫選根因。

1. 自動帶入站點、時間與借/還階段；若有營運整合再帶入車號與柱號，否則可掃描、選填或拍攝錯誤畫面。
2. 問可觀察症狀：沒有反應、顯示錯誤、扣款/解鎖異常、車卡住、明顯機械損壞、不確定。
3. 有明顯安全問題停止騎乘。借車尚未成功才建議換設備；交易或鎖定狀態不明先查證，避免誘導反覆扣款。还車未確認則保留現場證據並進入官方協助，不能假裝已停止計費。
4. 用戶可離開問卷，不必反覆試車替系統診斷。回報帶入進度，通知替代站但不保證可用。

證據→疑似根因→派單：

- 異常隨同一車號跨車柱出現：疑似車輛/車機，營運診斷後交授權車輛維修。
- 異常集中單一柱號且涉及不同車：疑似柱/鎖具，交站務設備維護。
- 同站多柱同時出錯：疑似供電、網路或站端系統，查設備心跳與錯誤碼。
- 同一使用者在多站失敗、其他人成功：疑似帳戶、付款或手機連線，交客服，對主管只顯示必要彙總。
- 證據不足：待診斷，不能扣成已確認壞車，也不能交一般車行維修車柱。

需整合租借結果/錯誤碼、車號-柱號對應、設備心跳、遠端診斷、維修驗收，才能更可靠區分。遠端自檢須由營運授權且保留操作紀錄，不由民眾任意解鎖或重啟。

數據面顯示：官方可借 5／已確認不可用 X／疑似異常 Y／確認時間；去除重複設備、注意官方已扣除者不得二次扣減，且歷史回報需過期或驗證。無單車/柱識別就不能可靠推導五輛均壞。以「服務可用性」補足名目庫存，確認全不可用可另開服務中斷事件。

72 小時未借僅是弱證據，站點庫存不變不代表同一輛車未動。若獲得單車旅次，才可做相對同站同車款使用強度的異常排序，不能直接判故障。

## 4. 比賽呈現與驗收

第一優先：事件台帳＋P0/P1手機決策＋設備分流工單；第二優先：有容量與時限的動態改派；第三優先：民眾獎勵、活動、雨天等既有能力接入。

五分鐘故事：官方顯示有5台→民眾回報借不到→診斷證據顯示疑似多柱失效→設備工單＋服務中斷事件→主管收到升級通知→比較改派方案→調度執行→設備/庫存恢復驗證→事件關閉與原因復盤。各段真實/模擬明示。

- 資料應用30%：歷史＋即時站況＋用戶症狀＋任务事件鏈；補齊資料缺口與來源時間。
- 技術可行性25%：可部署推播、持久事件、資源約束、診斷分流，Bedrock 僅整理已驗證資訊。
- 完成度25%：手機收到、人工確認、指派、狀態回傳、恢復與回放完整驗收。
- 主題契合20%：核心證明服務中斷偵測與調度改善，不只展示消費端獎勵。

量測：>30/>60 分鐘空滿站事件數、超標站分鐘、P90恢復時間、通知至確認/接單/抵達/恢復各段耗時、未指派事件比例、相同資源下的服務改善與里程、錯分診斷率。歷史半小時快照只能給相應精度；沒有真實需求和調度對照不可把模擬改善當實測。
