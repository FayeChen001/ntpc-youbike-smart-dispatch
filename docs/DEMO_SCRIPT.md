0. 開場（20 秒）：舞台頁。左手機框＝民眾端，右側＝政府端／微笑單車調度端，同一份預測。標籤說明：綠「真實計算」、紫「模擬」、藍「Bedrock」。

1. 通勤早峰｜江子翠（80 秒）
   - 點情境「通勤早峰｜江子翠」→ 時鐘 07:20。政府端：捷運江子翠站出口零位機率升高（早上是「無位可還」）。
   - 手機：規劃三方案 → 最快（4 號出口，零位風險高）、較穩（改還 3 號出口或文化路站）、順路集點（避開熱點得點）。Bedrock 生成一句理由。
   - 接受方案 → 「已登記意向」；政府端站點抽屜顯示「原始預測 vs 含意向修正」。強調：意向是配額不是預約。

2. 政府端預警與待查（60 秒）
   - 按 ▶ 播放 2–3 步。右上跳出告警：高（持續 90 分無車）、預警（120 分後零車機率）、節流摘要。
   - 切「待查清單」：雙零、24 小時無變化、容量矛盾，不派車。切「模型卡」：1–4 月訓練、6 月測試；180 分捷運站 MAE 8.6→5.6。

3. 演唱會散場｜新莊體育館（70 秒）
   - 點情境 → 18:00。調度端：18:30 起出現 🎤 任務（提前 180 分，目標 21:30–22:00），缺口摘要「派車可補 60，剩餘 159 靠民眾分流」。
   - 點任務：站點順序、載量、最遲出發、最早抵達（≥60 分前置）、Bedrock 簡報「情況如何」。
   - 手機「活動」：文化部 API 真實活動列表 + 情境活動卡 → 「散場怎麼走」三方案。

4. 放學接力｜土城國中（40 秒）
   - 點情境 → 15:00，播放到 15:30 收到「放學順路任務」通知；規劃 學校→捷運永寧站，順路集點方案給接力章。說明：只獎勵改善下一波需求的借還，不叫學生搬故障車。

5. 故障報修（30 秒）
   - 手機「報修」送出 → 政府端收到通知 → 播放幾步：授權店家接單（模擬）→ 驗收復役 → 結案核發維修回報章。

6. 收尾（20 秒）：AWS：Bedrock、S3、DynamoDB；限制與試辦條件：快照≠失敗旅次、候選鄰站≠到站成功、派車／商家／兌付為模擬、活動人數為情境。
